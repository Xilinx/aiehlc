# Design: deploying tiny-SD UNet with aiegraph "group offload"

Date: 2026-11-16
Status: draft, pending review
Related: `tutorial/model/tiny-sdm-unet.md` (the current approach, which produces the orange), `docs/plans/2026-09-09-aiegraph-primitive-fusion-offload-design.md` (fused offload on ResNet, a different problem)

---

## 1. Goal

Given a network, a user calls only aiegraph functions and gets an ELF that generates the orange on VEK385 (palmyra):

```
ONNX → ag.load → convert("a78") → [kernels generated from Python templates] → emod.offload_group(...) → emod.build → main.elf
```

- **Kernel templates** keep being generated by the current Python code (gemm_kacc in `unet_aie.py`, flash-attention in `fa_attn.py`).
- **Offload** (which call is replaced by what, and whether the replacement is correct) is done by aiegraph, instead of by scripts in the example directory rewriting `graph_driver.c`.
- **Performance** must not regress: the generated driver must be equivalent to the current one; on the board graph_run ≈ 1.295 s, 258 launches, cos 1.000000.

---

## 2. Current state: aiegraph is only half used

The flow of `example/aiegraph/unet_bk_sdm_tiny/build_unet.py`:

| Step | Done by |
|---|---|
| Load ONNX, convert to TVM C (`ag.load`, `convert("a78")`) | aiegraph |
| Build the AIE library | aiegraph's `emod.offload`, but **only on 1 "carrier layer"**, solely so that aiegraph calls aiehlc to build the whole `.cc` into a library |
| Replace the other 155 call sites with AIE | `build_unet.py` replaces `arm_build.generate_driver` (monkey patch) and rewrites the generated `graph_driver.c` with regexes: `unet_aie.patch_driver()`, `fa_attn`, `keep_layout_rt.keep_layout_driver()` |
| bf16 weights read in place, pre-laid-out in kacc block layout | regex deletes `graph_bf16_expand`; `prelayout_weights()` rewrites weights.bin |
| x86 check | calibrate and emulate are replaced with no-op functions, `offload(force=True)` |
| Link the ELF (`emod.build`) | aiegraph |

So today the user does not really "call aiegraph to offload".

## 3. Clarifying concepts: what "region" are we operating on

Terms like "region merging" and "region splitting" in the discussion are easy to confuse; this section pins them down.

- **TVM fused function**: TVM fuses several ONNX operators into one function, e.g. `reshape_transpose_multiply_reshape`, which corresponds to **one call** in `graph_driver.c`. This is already fixed by TVM; **we neither split it nor create a new, larger function.**
- **Replacement**: always **one call for one call** — either replaced by one AIE-side function, or deleted.
- **Group**: several **complete** TVM calls whose replacement functions, taken together, produce the same result as the original calls taken together. A group is only an **acceptance unit**: "these replacements are checked together".

### 3.1 Why aiegraph's current one-for-one replacement is not enough

aiegraph's current offload (`aiekernel/flow.py`, `arm_build.py:875`) has three implicit requirements:

1. Replacement is by **function name**: all calls of a function with the same name are replaced together;
2. The replacement function receives exactly the original call's arguments;
3. Each replacement function is compared individually against the original TVM function, and the results must match (calibrate).

Take UNet's attention group 0 as an example (calls [31]–[37] in `graph_driver.c`, all from TVM):

| Call | Original TVM function | What it originally computes | Replaced by | Individual comparison |
|---|---|---|---|---|
| [31] | `reshape_transpose_multiply_reshape` | writes the transposed, scaled Q | packs Q by stride from the linear's output `tensors[58]` (`[1][1024][320]`) into the kernel's staging area, multiplying in the 0.398 scale while packing | ✗ does not write Q |
| [32] | `…multiply_reshape_transpose` | writes Kᵀ | packs mean-subtracted K | ✗ |
| [33] | `nn_batch_matmul` | writes scores | **deleted** | ✗ |
| [34] | `nn_softmax` | writes P | **deleted** | ✗ |
| [35] | `reshape_transpose_reshape_transpose` | writes Vᵀ | packs V | ✗ |
| [36] | `nn_batch_matmul_1` | writes O in multi-head layout | launches flash-attention and writes O by stride **directly into `tensors[70]`** (`[1024][320]`, [37]'s output and the next linear's input) | ✗ |
| [37] | `reshape_transpose_reshape` | writes the merged O | **deleted** | ✗ |

Every call is replaced one-for-one, but:

- each replacement is **wrong when viewed individually**: the intermediate results (Q, Kᵀ, scores, P, Vᵀ) are never computed; only after the whole group finishes does `tensors[70]` match TVM;
- some replacements are "delete";
- [36] writes [37]'s output buffer, not one of its own arguments;
- the same TVM function name is shared by several groups (same shape means shared), so replacement must be by **call**, not by name.

This is why "groups" are needed: replacements are still done one by one, but **acceptance is done per group**.

### 3.2 Why the payoff is worth it

All numbers measured on the board (before KCO was enabled):

| Change | graph_run |
|---|---|
| attention on AIE, not fused (438 launches) | 2,680 ms |
| flash-attention fusion (softmax deleted, 258 launches) | 1,693 ms |
| plus keep-layout (56 layout calls deleted) | 1,650 ms |
| current (plus KCO) | 1,295 ms |

If aiegraph can only do naive one-for-one replacement, fusion is impossible and every UNet call is about 1 second slower.

## 4. How the current direct driver edit works

`unet_aie.py`, `fa_attn.py` and `keep_layout_rt.py` edit the text of `graph_driver.c` directly. The idea:

- **No call is moved**: every step stays at the position of some original call, so TVM's storage plan remains valid;
- **Intermediate state lives in the kernel's own static staging area** (`g_fa_qk`, `g_fa_v`), not in TVM's buffers;
- Asserts guarantee the edit is correct:
  1. The deleted functions really are pure permutations: regexes inspect the TVM function's C code (`_tvm_body`), and strides must be expected values such as H·D;
  2. Reading from the source instead is safe: the skipped intermediate tensor has exactly this one consumer (`_consumers(...) == [iq]`);
  3. Writing early is safe: [36] writes [37]'s output, and nobody touches that buffer in between (`_untouched`);
  4. Order is right: Q and K packing come before QKᵀ, V packing before PV, and each group deletes exactly one softmax;
  5. If any of these fails, the build fails.

The same idea is used elsewhere:
- **conv**: the AIE conv writes directly in the layout the next layer wants (`g_kl_y_14` gets a different shape tag), and the following layout call is deleted;
- **residual add**: merged into the linear's scatter;
- **temb**: the SiLU scale is folded into the weights at compile time, pre-laid-out and written into weights.bin.

**Weaknesses of this approach:**
- It matches generated C text; if the output format of `arm_build.py` changes, the regexes can break (this caused conflicts when cherry-picking GIN);
- The semantics of TVM functions are judged by regexes over code, and the function-name patterns (`Q_FN`, `K_FN`) are UNet-specific;
- The contracts between steps (the order of roles 2/3/5/6, the static buffers) exist only in C code; aiegraph does not know about them;
- There is no x86 check; only the whole-network cos from a board run serves as a safety net.

The design below **keeps the board-proven model of "no call is moved + the kernel manages intermediate state itself"**, and only moves matching, placement and checking out of regex edits of C text into aiegraph, done on the graph.

## 5. Interface

### 5.1 Principles

The user **does not write "replace call 31 with X"**, but declares only three things:

1. **Which group**: found by pattern matching (attention, conv, ...), or given as a set of ONNX nodes;
2. **The group's boundary data**: tensors flowing into the group from outside and tensors flowing out. Computed by aiegraph, with shape, layout and row pitch;
3. **How many steps the kernel has, and which boundary tensor each step reads or writes.**

Where each step is placed, which calls are deleted, and the checks and validation are all done by aiegraph.

### 5.2 Python (written by the user)

```python
import aiegraph as ag
import unet_aie, fa_attn                      # Python templates, stay in the example directory

emod = ag.load("unet_sim.onnx").convert("a78")

# ---- attention: one group = 7 TVM calls ----
groups = emod.match("attention")              # 18 groups
g = groups[0]
g.calls        # [31, 32, 33, 34, 35, 36, 37]
g.q, g.k, g.v  # tensors flowing in from outside the group: tensors[58/59/60], [1][1024][320] fp32, ld=320, one column block per head
g.o            # tensor flowing out: tensors[70], [1024][320]
g.scale        # 0.398: the scale TVM fused into the transpose function, extracted by the matcher from the Relay graph
g.cls          # shape class (several groups share one kernel instance)

fa_src = fa_attn.generate(groups)             # generates the kernel and the step functions from g.q.shape, ld, etc.

for g in groups:
    emod.offload_group(g, fa_src, steps=[
        ag.step("fa_pack_q", reads=g.q, consts=dict(cls=g.cls, s=g.scale)),
        ag.step("fa_pack_k", reads=g.k, consts=dict(cls=g.cls, s=g.scale)),
        ag.step("fa_pack_v", reads=g.v, consts=dict(cls=g.cls)),
        ag.step("fa_run_o",  writes=g.o, consts=dict(cls=g.cls)),
    ])

# ---- conv / linear: one group has only 1 call, 1 step ----
for g in emod.match("conv", partition="partition_p4a.json"):
    emod.offload_group(g, kacc_src, steps=[
        ag.step("unet_aie_conv", reads=g.x, writes=g.y,
                weights=g.w.as_bf16(layout="kacc"),     # weight contract: bf16, pre-laid-out, not expanded on the A78
                consts=g.geom)])                       # cid, stride, pad

# ---- keep-layout: the AIE conv call + the layout call after it = one group ----
for g in emod.match("conv+layout"):
    emod.offload_group(g, kacc_src, steps=[
        ag.step("unet_aie_conv", reads=g.x, writes=g.y_after_layout, weights=..., consts=...)])

# ---- temb: SiLU scale folded into the weights (compile-time transform) ----
for g in emod.match("temb_dense"):
    emod.offload_group(g, kacc_src, steps=[...],
                       weight_transform=lambda w, s: (w * s).astype("bfloat16"))

emod.build("a78", runtime_io=..., layer_cflags=...)    # same as today
```

Every case uses the same interface; the only difference is how many calls a group has.

### 5.3 C (in the template-generated `.cc`)

All step functions use the same calling convention (ABI) and, like today's `AIEK_SPEC`, declare what they read and write:

```c++
AIEK_STEP(fa_pack_q, reads(1), writes(0), consts(cls, s))
int fa_pack_q(const aiek_buf *in, aiek_buf *out, const aiek_const *c);  /* pack into the kernel's static staging area */

AIEK_STEP(fa_run_o, reads(0), writes(1), consts(cls))
int fa_run_o(const aiek_buf *in, aiek_buf *out, const aiek_const *c);   /* launch FA, write O by stride */
```

`aiek_buf` = pointer + shape + row pitch + dtype, so the kernel does not need to guess the layout. aiegraph uses `AIEK_STEP` to check that the Python-side `ag.step(...)` declarations agree.

## 6. What aiegraph does internally

| Stage | Rule |
|---|---|
| **Match** | `match("attention")` builds on the existing `partition.match_attention` (at the ONNX level), then maps to TVM calls: weighted operators by weight fingerprint (already in `region.py`), activation-only operators by dataflow. A group must consist of **complete** TVM calls; a call that is half inside and half outside the group is an error. Fused constants (scale) are extracted from the Relay graph |
| **Boundary** | A tensor read inside the group but produced outside it = input; a tensor produced inside the group and read outside it = output. Both carry shape and layout |
| **Placement** | A step that reads an input is placed at the position of the earliest call in the group that reads that tensor (the data is guaranteed to still be there); a step that writes an output is placed after the steps it depends on. No call outside the group is moved, and TVM's storage plan stays unchanged |
| **Deletion** | All other calls in the group are deleted. Precondition: nobody outside the group reads the intermediate tensors they produce; otherwise it is an error |
| **Early write** | If a step that writes an output runs earlier than the original producer ([36] writes [37]'s output), no call in that interval may touch the buffer; otherwise it is an error |
| **Pure-permutation test** | If a deleted call is a layout/reshape/transpose, its operators are inspected on the Relay graph rather than by regexes over C code |
| **Weights** | `weights=...as_bf16(layout=...)`: this layer's weights are stored in weights.bin as bf16 in the layout the kernel wants, and the driver no longer calls `graph_bf16_expand` for it. `weight_transform` is a compile-time transform hook |
| **x86 check** | Run the group's chain of TVM C functions in original order on the boundary inputs as the reference; then run the steps in kemu in their placed order; compare the outputs. Only this group runs, not the whole network, so the cost is small and `force=True` is no longer needed |
| **Build** | All steps are in one `.cc`, built into one library with a single `routing()` (GAP ea6615). The warm start, KCO and control packet pragmas are unchanged |
| **Record** | Each group is written into `layers/partition.json`: group id, member calls, each member's action, steps and constants. `offload_reset` can revert a whole group |

### 6.1 Generated driver (equivalent to today's)

```c
/* [31] */ fa_pack_q(&(aiek_buf){tensors[58] ...}, 0, &(aiek_const){.cls = 0, .s = 0.398f});  /* group attn0 */
/* [32] */ fa_pack_k(...);
/* [33] [34] removed: group attn0 */
/* [35] */ fa_pack_v(...);
/* [36] */ fa_run_o(0, &(aiek_buf){tensors[70] ...}, ...);
/* [37] removed: group attn0 (o written by fa_run_o at [36]) */
```

This is the same thing as today's `unet_aie_attn_kl(4, 2, 0, tensors[58].data, 320, 0, 0, 0.398f)`.

## 7. Performance impact

- **In principle, none.** How fast the board runs depends only on the final driver and kernel, not on who generated them. As long as the generated driver is equivalent to today's (calls, weights read in place, one library, warm start, KCO), the ELF is equally fast.
- **Performance drops only when a missing feature forces a fallback.** No group support → no fusion, about +1 s; no keep-layout support → about +43 ms; weights fall back to fp32 → every call has to re-lay-out about 0.65 GB of weights at run time (not measured, but the cost will not be small).
- The x86 check only slows down compilation; it does not affect run time.

## 8. Implementation plan

**Acceptance for every step:**
1. The generated `graph_driver.c` is equivalent to the baseline (diff only in names and comments);
2. Board smoke test: graph_run ≈ 1.295 s, 258 launches, cos 1.000000, `aot_fallbacks=0`;
3. At the last step, rerun the tutorial's orange: 50/50 calls cos_OK.

| Step | Content | When done |
|---|---|---|
| S0 | Save the baseline: current `graph_driver.c`, hash of weights.bin, smoke log, orange | A reference to compare against |
| S1 | **Per-call replacement + step ABI + bf16 weight contract**: `offload_group` supports a one-call group; `AIEK_STEP`; `weights=` and `weight_transform` | conv and linear go through aiegraph directly; this part of `patch_driver` is deleted |
| S2 | **Groups**: multiple calls, placement, deletion, early-write checks (done on graph.json); partition.json records groups; `offload_reset` reverts a whole group | Unit tests: a deliberately overwritten buffer and an intermediate tensor with a reader outside the group must both raise errors |
| S3 | **Attention matching**: move the `map_attn` logic into aiegraph, `emod.match("attention")`, take scale from Relay | flash-attention goes through aiegraph; `_remove_fa_softmax` is deleted |
| S4 | **Group-level x86 check**: chained subgraph reference vs kemu | Remove `force=True` and the no-op function patches |
| S5 | **keep-layout and temb**: hook up the existing `partition.plan_keep_layout` (currently planning only, codegen not wired, GAP 6a9d38); pure-permutation test done on Relay | Delete `keep_layout_rt.py` |
| S6 | Rewrite the tutorial as pure aiegraph calls; `build_unet.py` keeps only "generate templates + declare groups" | New tutorial, orange regenerated |

S2 and S3 are the main workload; S1, S4 and S6 are fairly straightforward.

## 9. Open questions

1. **Matcher generality**: the attention matching rules first cover only bk-sdm-tiny's 6 classes, and are extended when switching models (e.g. SDXL). Should users be able to give an ONNX node list directly as a fallback?
2. **Step state**: intermediate state is in the kernel's static staging area, so only one instance of a group can be in progress at a time. Execution is single-threaded and sequential today, so this is fine; it must be revisited when multiple groups run in parallel.
3. **Compatibility with by-name replacement**: the existing ResNet flow replaces by function name. The new interface replaces by call; the old interface is kept as shorthand for "make each call of this name its own group".
4. **x86 check tolerance**: between bf16 weights and the fp32 reference, judge by cos ≥ 0.999 plus a maxabs threshold. Should the exact thresholds follow the tutorial runner's settings, or be stricter?
