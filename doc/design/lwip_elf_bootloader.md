# netboot: resident lwIP ELF loader for the baremetal A78

**Status:** mode D (section 7a) **implemented** in `src/tool/netboot/`
(README there), driven by `apppaltest.py --netload`. Section 12 records what the
board taught us; it overrides earlier sections where they disagree (notably the
memory map). **Goal:** replace the per-run
`xsdb dow -force <elf>` (slow JTAG) with a loader that stays on the board, takes
the ELF over Ethernet, and runs it. JTAG is used once per power cycle, or never
if the loader boots from flash.

## 1. Why

The board ELF is 12.5 MB of loadable bytes, and 94% of it is the weight blob:

| `main.elf` section | bytes | downloaded by `dow` |
|---|---|---|
| `.text` | 0.13 MB | yes |
| `.rodata` | 0.63 MB | yes |
| `.data` (`weights.bin`) | **11.8 MB** | yes |
| `.bss` | 31 MB | no (zeroed by crt0) |

All of that crosses JTAG on every `apppaltest.py` run. Over 1 GbE with lwIP RAW
TCP, a sustained 30-60 MB/s is a conservative expectation for a baremetal A78
with caches on, which puts the transfer at **~0.2-0.4 s**. Validate this
number in phase 1 (section 9) before relying on it.

segment)? Without that, the design falls back to the JTAG paths in section 10.

## 3. Architecture

```
 dev box ── ssh/scp ──► PALIP lab host ───────── 1GbE ─────────► board GEM0
 (build)               netload.py (TCP client)                  netboot.elf (TCP server, lwIP RAW)
                       xsdb only for: one-time loader load        │ stage ELF in DDR_LOW1
                                     and recovery                 │ validate + place PT_LOAD into DDR_LOW0
                       com0 UART ◄────────── console ─────────────┤ quiesce GEM/GIC, clean caches, MMU off
                                                                  └► jump app e_entry (EL3, reset-like state)
```

### Memory map (as measured on the board, see section 12)

| Region | Owner | Use |
|---|---|---|
| `0x0 .. 0x77FF_FFFF` | **app** | every existing ELF; the loader refuses a `PT_LOAD` reaching `0x7800_0000` |
| `0x7800_0000 .. +32 MB` | **supervisor** image, heap, stacks, lwIP pools | its own `lscript` (generated by `build.sh`) |
| `0x7A00_0000 .. +2 MB` | **GEM BD ring** | alone in its 2 MB MMU block: the port makes that block non-cacheable |
| `0x7A20_0000 .. 0x7FFF_FFFF` | **staging** | received ELF file as-is (~94 MB cap) |

The app ELFs use `0x0 .. ~0x42C9_AE80` (1 GB `.heap` included), and AIE buffers come
from that heap (`XAie_MemAllocate`), so the top 128 MB of the 2 GB is free for the
supervisor. **`0x8_0000_0000` ("DDR_LOW1") is NOT usable on this board**: it
mirrors `DDR_LOW0` (section 12).

## 5. Protocol (TCP, one ELF per connection)

```
host → board   header (64 B, little endian)
                 u32 magic  = 'NBT1'
                 u32 version = 1
                 u64 elf_size
                 u8  sha256[32]
                 u32 flags         bit0 = run after load, bit1 = reply with load map
                 u32 reserved
               payload: elf_size bytes (raw ELF file)
board → host   status (32 B): u32 magic 'NBR1', i32 rc, u64 bytes_rx,
               u32 rx_ms, u32 place_ms, u64 entry
               rc != 0 → reason string follows (≤ 256 B); the loader stays up
```

Loader steps, in order. Any failure replies `rc<0` and keeps listening, so a bad
upload never bricks the session:

1. Receive into staging with `tcp_recved()` flow control. Reject
   `elf_size > staging`.
2. Check SHA-256 (mbedTLS from the BSP, or a small standalone implementation).
   This catches truncated or corrupted uploads, not attackers (section 8).
3. Validate the ELF header: `ELFCLASS64`, `EM_AARCH64`, `ET_EXEC`, and the
   program headers inside the file.
4. For each `PT_LOAD`: require `[p_paddr, p_paddr+p_memsz)` ⊂ `DDR_LOW0`. Then
   `memcpy p_filesz` bytes and zero `p_memsz - p_filesz`. The `.bss` zeroing is
   redundant with crt0 but makes the image correct regardless of crt0.
5. Send the status reply and wait for `tcp_sent` to drain it, so the host sees
   rc=0 *before* the board leaves lwIP.
6. Hand off (section 6) to `e_entry`.

TFTP was considered (lwIP ships a server example). It was rejected because it
uses 512-byte lock-step blocks, so throughput is RTT-bound, and it has no
"run now" verb. TCP with a 64 KB window is the fast and simple option.

## 6. Hand-off: make the app see a reset-like CPU

The app's `boot.S` (standalone BSP, EL3) assumes it starts from reset: it
installs its own vector table and translation table, enables the MMU and caches,
and initializes the GIC if it uses one. The loader must leave nothing behind
that conflicts with that:

1. **Stop the NIC first.** Disable GEM0 TX/RX (`XEmacPs_Stop`), mask its IRQ,
   and wait for DMA idle. A GEM DMA landing in `DDR_LOW1` after the jump is
   harmless to the app, but a late RX descriptor fetch while the app reprograms
   memory is not. Stop it.
2. **Quiet the GIC.** Disable the GEM interrupt and the CPU interface
   (`GICC_CTLR`/`ICC_IGRPEN1_EL3 = 0`) and clear pending IRQs. Mask DAIF.
3. **Make memory coherent for an MMU-off start.** Clean and invalidate D-cache
   by VA over every placed `PT_LOAD` range (`Xil_DCacheFlushRange`), then the
   whole D-cache (`Xil_DCacheFlush`). Invalidate the I-cache (`IC IALLU`), then
   `DSB ISH; ISB`.
4. **Turn the MMU and caches off.** `SCTLR_EL3 &= ~(M|C|I)`, `TLBI ALLE3`,
   `DSB; ISB`. This matches a cold start, so the app's `boot.S` runs its normal
   path.
5. Load a fresh stack pointer in `DDR_LOW1` scratch (the app replaces it at
   once), put `x0 = mailbox address` (ignored by today's apps, available to
   future ones), and `br e_entry`.

Steps 3-5 live in `handoff.S`: once the MMU is off, the C code that follows
would run from an uncached alias, so keep it in assembly with no stack use.

**AIE state is unchanged** compared with today's `-nonreboot` flow. The PL and
AIE partition are not reset by `rst -proc` today either, and conv2dstem is
built with `AIE_DEBUG_FLAG_DISABLE_PARTITIONTEARDOWN`, so repeated runs over
an already-initialized partition are the current, tested situation.

## 7. Getting back to the loader after a run

The app owns the CPU once it runs. Three ways back, all supported, cheapest
first:

| Mode | How | App change |
|---|---|---|
| **A. JTAG re-entry** (default) | `netload.py --reset` (or `apppaltest`): xsdb `stop; rwr pc 0x8_0000_0000; con` | none |
| **B. Return on `exit()`** | link `src/tool/netboot/app_return.c` into the app: `_exit()` jumps to the loader warm entry (address in the mailbox, checked against a magic) | opt-in, one object |
| **C. Cold boot** | put the loader into `BOOT.BIN` as the A78 partition: it is then the first thing to run after `power 1` | changes `PALBOARD_BIN` packaging |

The **loader warm entry** re-runs its own init: re-enable the MMU and caches,
re-init the GIC, re-init GEM0 and lwIP from scratch. It must never assume its
own `.data` survived the app. The app does not touch `DDR_LOW1`, but the warm
entry still re-derives everything from `.data`'s load image, so that a stray
write cannot leave it half-alive. Mode A writes only one register over JTAG, so
it costs milliseconds, not the per-byte download.

## 7a. Recommended mode D: supervisor on core 0, app on core 1 (watchdog)

Modes A-C still need JTAG or a power cycle when an app hangs. The APU has eight
A78 cores (`PM_POWER_ACPU_0_0 .. 1_3` in `xpm_nodeid.h`), so the loader can
stay **alive** on core 0 as a supervisor, run every app on **core 1**, and kill
and relaunch it on command or on timeout, with no JTAG at all.

```
core 0 (never leaves netboot)                       core 1 (the app, reset per run)
  lwIP TCP server, POLLED (no GIC IRQ)                boot.S (unchanged BSP) -> main()
  receive + validate + place ELF into DDR_LOW0        optional: heartbeat++ / exit code
  XPm_RequestWakeUp(ACPU core1, entry)  ──────────►   runs; owns the AIE
  watchdog loop: heartbeat age, run time limit
  XPm_ForcePowerDown(core1) on kill / timeout / new ELF
  AIE partition reset before the next launch
```

### Why this is feasible with this BSP (checked)

* `boot.S` does **not** park secondary cores: the `MPIDR != 0 → wfi` block is
  `#if 0` ("don't put other a53 cpus in wfi"). RVBAR is computed per core from
  `MPIDR`, so an unmodified app image boots on core 1.
* `libxilpm_ng.a` is already in the BSP. Core 0 drives core 1 through the PLM:
  `XPm_RequestWakeUp(<core1 device>, 1, e_entry, 0)` starts it at the ELF entry,
  and `XPm_ForcePowerDown(<core1 device>, ...)` (or `XPm_ResetAssert`) stops it,
  **whatever it is doing**. That is the watchdog's kill switch, and it does not
  depend on the app cooperating.
* Memory split as in section 3: app in `DDR_LOW0`, supervisor in `DDR_LOW1`.
  Each core has its own MMU tables and stack, so the two images never share a
  stack the way two copies of the same image would (`EL3_stack` is one symbol).

A side benefit: **section 6 (MMU-off hand-off) is not needed in mode D.**
Core 1 comes out of a real PLM reset at `e_entry`, so the cache, MMU and GIC
state it sees is genuinely reset state. Core 0 only has to clean the placed
ranges to the point of coherency (`Xil_DCacheFlushRange`) before the wake-up.

### Commands (same TCP port, header `flags`)

| Command | Effect |
|---|---|
| `LOAD_RUN` | kill core 1 if running → place ELF → AIE reset → wake core 1 |
| `RERUN` | relaunch the **already placed** image: no transfer at all. The image must be re-placed only if the app wrote its own `.data` (true for most C apps), so the supervisor keeps the staged ELF and re-copies `PT_LOAD` (~10 ms for 12.5 MB in DDR) |
| `KILL` | force core 1 down; reply with its last heartbeat and run time |
| `STATUS` | idle / running / exited(rc) / killed(reason), heartbeat age, uptime |
| `CONSOLE` (opt.) | stream the app's console ring (see below) |

### Watchdog

Three triggers, any one of which kills core 1:

1. **Remote**: `KILL`, or a new `LOAD_RUN`, arrives. This always works, even
   if the app is stuck in a spin or a `wait_io` loop.
2. **Wall-clock limit** per run (`timeout_ms` in the header; default 600 s,
   matching apppaltest's watchdog).
3. **Heartbeat (opt-in)**: the app links `src/tool/netboot/app_hb.c`, which
   bumps a counter in the mailbox from `main()` and from `__Runtime_wait_io`'s
   poll loop. If the counter does not move for `hb_ms`, kill. Apps that do not
   link it are covered by 1 and 2 only.

Exit is reported the same way. The `app_hb.c` `_exit()` writes `rc` to the
mailbox and parks core 1 in `wfi`, and the supervisor powers it down. Without
`app_hb.c`, an app that returns from `main` just stops making progress, and
the time limit or the next `LOAD_RUN` reclaims the core.

### Hazards specific to two cores, and the rule for each

| Hazard | Rule |
|---|---|
| **App `boot.S` invalidates D-caches by set/way up to LoC** (`invalidate_dcaches`). If LoC covers the cluster-shared L3, that can **discard core 0's dirty lines** | (1) supervisor cleans its D-cache (`Xil_DCacheFlush`) **immediately before every wake-up** and keeps its run-time state small; (2) lwIP pbufs and GEM BD rings in a **Normal non-cacheable** region of `DDR_LOW1`, so nothing of value is in cache; (3) phase-D1 test: stress the supervisor's TCP path while core 1 boots 100 times. If it ever corrupts, carry a one-line app `boot.S` override that limits set/way invalidation to L1/L2 |
| **Shared GIC distributor**: an app that calls `XScuGic_CfgInitialize` resets the distributor | supervisor runs lwIP **polled** (`xemacif_input` in its main loop, no interrupts), so it needs nothing from the GIC |
| **Shared UART** | supervisor prints only between runs. During a run the console belongs to the app. Optional: redirect app `outbyte()` to a mailbox ring that `CONSOLE` streams over TCP, which removes the dependence on `com0` |
| **AIE left mid-DMA by a kill** | before every launch the supervisor resets the app's AIE partition through the PLM (`XPm_ResetAssert` on the AIE partition, or `XAie_PartitionInitialize` with reset options), so the next app never inherits running DMAs or held locks. Today's `-nonreboot` flow has the same exposure; mode D removes it |
| **PLM permissions**: core 0's subsystem must be allowed to request/force-off core 1 | phase-D0 check: `XPm_RequestWakeUp` / `XPm_ForcePowerDown` return `XST_SUCCESS`. If the PDI's CDO denies it, the PDI subsystem definition must put both cores in one subsystem (`PALBOARD_BIN` change) |
| Two cores share `XPAR_CPU_ID 0` in the BSP | only matters for code that keys on `XPAR_CPU_ID`; the app does not. Build the app unchanged and check `MPIDR` in phase D1 |

## 8. Safety and failure handling

* **Not a security boundary.** Anyone on that segment can run code on the
  board. Bind to the lab VLAN only; an optional `NETBOOT_TOKEN` in the header
  guards against accidental cross-talk between users, not attackers.
* Every validation failure replies and keeps serving. Only a successful,
  verified load leaves the loader.
* In modes A-C a hung app needs mode A or a power cycle, exactly as today, and
  `apppaltest.py` keeps its watchdog and its `rst -proc` recovery. **Mode D
  (section 7a) removes this:** the supervisor kills and relaunches the app core
  without JTAG.
* The loader prints one line per upload on the UART
  (`[netboot] rx 12.5 MB in 312 ms, entry 0x0, jump`), so console logs stay
  self-describing.

| Option | Gain | Cost |
|---|---|---|

on com0. That is the same result as a JTAG run.

## 13. Protocol version 2: admission ack, max run time, forced runs (2026-10-23)

Version 1 told a client nothing until the whole request was in: a `LOAD_RUN` to a
busy app core was refused only after the full ELF (15-26 MB) had crossed, and a
second connection during a transfer got a TCP reset. Version 2
(`netboot_proto.h`) adds an **ack** that the supervisor sends as soon as the
64 B header arrives, before any payload:

```
host -> board   netboot_req (64 B)       version = 2, flags bit0 = FORCE, max_run_ms
board -> host   netboot_ack (48 B + msg) verdict, state, core, run_ms, max_run_ms,
                                         remaining_ms, retry_after_ms, can_stop, runs
host -> board   payload                  only if verdict == OK
board -> host   netboot_rep (48 B + msg) unchanged
```

| verdict | when | client action (`netload.py` exit code) |
|---|---|---|
| `OK` | app core free or parked; or a forced run terminated an app past its max | send the ELF (0) |
| `BUSY` | an app runs within its `max_run_ms` | retry after `retry_after_ms`; `--wait N` polls every <= 2 s (3) |
| `OVERTIME` | the app ran past its `max_run_ms`, request not forced | resend with `--force` (4) |
| `STUCK` | forced, but the PLM refuses to stop the app core (palmyra, section 12 item 4) | re-bootstrap; `apppaltest --netload` does it (5) |
| `SERVING` | another client's request is in progress (one at a time) | retry after 0.5 s (3) |
| `REJECT` | malformed header | fix the request (1) |

**Max run time.** Each run carries `max_run_ms` (the old `timeout_ms` field);
0 means `NETBOOT_DEFAULT_MAX_RUN_MS` = **60 s** (was 600 s). Past it the watchdog
tries to stop the app core; where the PDI refuses, the run is marked
`watchdog-timeout` and stays busy until it exits or is forced. An app that exits
after its limit is still detected (`exited`). `apppaltest --netload` stops its
console wait on `exited`, `killed` or `watchdog-timeout`.

**Forced run.** `FORCE` only preempts an app *past* its limit; an app within its
limit is never preempted (`BUSY`). The supervisor stops the old app through the
PLM kill chain (power-down, warm reset, cold reset). On palmyra the PLM refuses
all three, so the verdict is `STUCK` and the client terminates the app by
re-bootstrapping (power cycle + `device program`). `can_stop` in the ack says
which case the board is in (1 yes, 0 refused, 2 not tried yet).

**Freeing a stuck core without a re-bootstrap (JTAG park).** Every ack carries
`park_addr`, the running supervisor's `nb_park`. For a `STUCK` verdict,
`apppaltest --netload` opens xsdb on the lab host and, on core 1 only, runs
`stop; rst -proc; rwr pc <park_addr>; con`: the core restarts out of reset
straight into the park routine and the supervisor reuses it like any parked
core (`status` says `app core parked`). Then it re-sends the ELF. That is
**16-19 s** wall for the whole `apppaltest` run instead of ~60 s with a power
cycle + `device program`; it falls back to the re-bootstrap if the park fails
or the supervisor predates `park_addr`. It relies on the polled supervisor
(section 12 item 9): the reset leaves the GIC disabled. AIE state carries over,
as with any parked-core reuse; a following ResNet-18 run was bit-exact.

Polled vs interrupt-driven lwIP, 26.4 MB ELF, 5 runs each: board receive
median 839 ms (810-863) vs 837 ms (828-932); client send median 1.52 s vs
1.58 s -- no change.

**Compatibility.** The supervisor still serves version-1 requests (no ack). A v2
client talking to a v1 supervisor gets the v1 error reply, detects it and says
to re-bootstrap, which `apppaltest --netload` does on its own.

Measured on palmyra with `src/tool/netboot/test/nbspin.c` (busy-waits N s):
`BUSY` with the exact time left; `OVERTIME` at 11.4 s of an 8 s max; `STUCK` with
`--force`; `exited` detected after the timeout; `SERVING` for a second client
while one connection is held mid-header; a v1 client still served;
`apppaltest --netload` waited 21.7 s for a 20 s app (polling every 2 s) and then
ran ResNet-18 without a power cycle; with the old app past a 3 s max it forced a
re-bootstrap and ran ResNet-18 (43 s wall).
